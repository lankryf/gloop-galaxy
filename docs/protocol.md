# Протокол Gloop Galaxy

Усі числа little-endian. Службові повідомлення (вхід у кімнату, чат, список гравців, ping) – текстові JSON-кадри формату `{ "v": 0, "type": ..., ... }`, вони описані в README (лаба 4). Тут описано бінарні кадри, які йдуть 30 разів на секунду.

Версія бінарного формату: **1** (байт 1 кожного кадру). Клієнт може попросити JSON замість бінарного формату: `join { codec: "json" }`, тоді ті самі дані йдуть як `{ "type": "input", "inputs": [...] }` і `{ "type": "snapshot", ... }`.

## Input (клієнт → сервер), тип 1

| Зсув | Тип | Поле |
|---|---|---|
| 0 | Uint8 | тип повідомлення = 1 |
| 1 | Uint8 | версія = 1 |
| 2 | Uint8 | `n` – кількість записів, 1–16 |
| 3 + 5·i | Uint32 | `seq` запису i |
| 7 + 5·i | Uint8 | кнопки запису i: біт 0 – газ, 1 – вліво, 2 – вправо, 3 – постріл |

Розмір: `3 + 5n` байтів. Клієнт кожен крок надсилає останні 3 введення (поточне і два попередні), тому втрата одного кадру нічого не ламає: сервер бере записи з `seq` більшим за вже отриманий.

## Snapshot (сервер → клієнт), тип 2

Заголовок, 12 байтів:

| Зсув | Тип | Поле |
|---|---|---|
| 0 | Uint8 | тип повідомлення = 2 |
| 1 | Uint8 | версія = 1 |
| 2 | Uint32 | `tick` – номер кроку сервера |
| 6 | Uint32 | `ack` – останній `seq` цього гравця, який сервер обробив |
| 10 | Uint16 | кількість сутностей |

Далі сутності. Кожна починається з 11 байтів:

| Зсув | Тип | Поле |
|---|---|---|
| 0 | Uint16 | `id` |
| 2 | Uint8 | `kind`: 1 корабель, 2 куля, 3 астероїд, 4 бонус, 5 гравітаційний об'єкт |
| 3 | Float32 | `x` |
| 7 | Float32 | `y` |

Потім поля залежно від `kind`. Кути передаються як Int16 в одиницях 1/10000 радіана (діапазон ±3,2767, тобто весь [-π, π]).

**Корабель (26 байтів разом):** `vx` Float32, `vy` Float32, `angle` Int16, `hp` Uint8, `flags` Uint8 (біти: 0 газ, 1 мертвий, 2 щит, 3 швидкий вогонь, 4 самонаведення, 5 бот), `score` Uint16, `respawn` Uint8 (десяті частки секунди до появи).

**Куля (25):** `vx` Float32, `vy` Float32, `owner` Uint16 (id корабля), `shot` Uint32 (`seq` введення, яким її випущено; 0 для ботів).

**Астероїд (15):** `angle` Int16, `radius` Uint8, `hunter` Uint8 (0/1).

**Бонус (12):** `type` Uint8 (0 щит, 1 швидкий вогонь, 2 самонаведення).

**Гравітаційний об'єкт (24):** `vx` Float32, `vy` Float32, `angle` Int16, `type` Uint8 (0 чорна діра, 1 планета), `timeLeft` Uint16 (десяті частки секунди; 65535 – вічний).

Після сутностей іде Uint8 – кількість подій, і події по 12 байтів:

| Зсув | Тип | Поле |
|---|---|---|
| 0 | Uint8 | тип: 1 постріл, 2 влучання, 3 вибух, 4 очки, 5 бонус, 6 поглинання, 7 колапс діри |
| 1 | Float32 | `x` |
| 5 | Float32 | `y` |
| 9 | Uint16 | `a` – зазвичай id корабля |
| 11 | Uint8 | `b` – розмір вибуху ×10, очки / 10, тип бонусу або що саме поглинуто |

Декодер перевіряє тип, версію, довжину кожної сутності і загальну довжину кадру. Якщо щось не сходиться, він кидає `CodecError`, а не повертає сміття. На сервері зламаний кадр від клієнта закриває сокет з кодом 4000.

## Точність

Сервер після кожного кроку округлює стан кораблів так само, як їх передає: координати і швидкість – до Float32 (`Math.fround`), кут – до 1/10000 рад. Тому клієнт отримує точно той стан, з якого сервер рахуватиме далі, і передбачення після звірки збігається до біта.
